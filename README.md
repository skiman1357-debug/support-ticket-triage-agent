# Support Ticket Triage Agent

A deployed portfolio application that helps support staff classify customer tickets,
assign priorities, and prepare reply drafts grounded in a small knowledge base.
It combines semantic retrieval with structured LLM output and explicit human-review flags.

Built for **CloudDesk**, a fictional service, using synthetic support documents.
The application drafts replies; it does not send messages, verify payments,
modify accounts, or route tickets to a real support team.

## What it does

- Classifies tickets as `billing`, `account_access`, `technical`, `security`, or `other`.
- Assigns `low`, `normal`, `high`, or `urgent` priority.
- Retrieves the three most similar knowledge documents using local CPU embeddings.
- Produces an English reply draft with source IDs and a knowledge-sufficiency flag.
- Flags cases needing human review and explains the reason.
- Displays cited documents and lets the reviewer download the draft as a text file.
- Keeps the result in Streamlit session state so displaying sources or downloading
  a draft does not trigger another analysis.

## How it works

1. The user unlocks the Streamlit interface and submits a ticket.
2. Streamlit sends the ticket to FastAPI with an `X-API-Key` header.
3. FastAPI validates the input and retrieves relevant knowledge documents.
4. The xAI model receives the ticket and retrieved documents and returns a structured result.
5. Python validates the result and source references. Source contents are populated
   from the retrieved documents, rather than generated by the model.
6. Streamlit displays the draft, priority, review reason, and supporting documents.

The embedding model and document embeddings are loaded once per API process.
Normalized embeddings are compared using a dot product, equivalent to cosine similarity.
Similarity scores are not confidence probabilities.

## Knowledge base

The application uses six synthetic documents in `data/knowledge_base.json`.
These define the supported procedures; they are not a fixed list of accepted questions.

| Document | Topic |
| --- | --- |
| KB-001 | Account blocked after payment |
| KB-002 | Password reset |
| KB-003 | Unexpected or duplicate charge |
| KB-004 | Application errors |
| KB-005 | Subscription renewal cancellation |
| KB-006 | Suspected account compromise |

If the supplied documents do not support an answer, the expected result is
`knowledge_sufficient=false`, no cited sources, and human review.
Retrieval always returns the top documents; there is no similarity rejection threshold.

## Local setup

Clone the repository and use Python 3.13. The commands below use Windows PowerShell.

```powershell
git clone https://github.com/skiman1357-debug/support-ticket-triage-agent.git
cd support-ticket-triage-agent
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt -r requirements-api.txt
Copy-Item .env.example .env
```

Edit `.env` locally and set:

```dotenv
XAI_API_KEY=YOUR_XAI_API_KEY
XAI_MODEL=YOUR_AVAILABLE_XAI_MODEL_ID
TRIAGE_API_KEY=YOUR_RANDOM_SHARED_API_KEY
TRIAGE_API_URL=http://127.0.0.1:8000
DEMO_ACCESS_CODE=YOUR_SEPARATE_DEMO_CODE
```

Use a model available to your xAI account that supports the structured-output
request used in `triage_agent.py`. The deployed project was tested with `grok-4.7`.

Generate a random shared API key locally with:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Keep `.env` and `.streamlit/secrets.toml` out of Git. Never put real credentials
in the README. The demo code and API key serve different purposes and should differ.

Start the API in one terminal:

```powershell
python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

Start the interface in a second terminal with the same virtual environment active:

```powershell
python -m streamlit run app.py
```

Open `http://localhost:8501`. Local API documentation is at
`http://127.0.0.1:8000/docs`. The first API startup downloads the embedding model.

## API

| Endpoint | Authentication | Purpose |
| --- | --- | --- |
| `GET /health` | Public | Reports readiness and knowledge-document count |
| `POST /triage` | `X-API-Key` | Retrieves documents and generates a validated triage result |

Example request body:

```json
{
  "id": "DEMO-001",
  "subject": "Account blocked after payment",
  "message": "I paid my subscription invoice yesterday, but my account is still blocked."
}
```

The response contains `category`, `priority`, `knowledge_sufficient`,
`needs_human_review`, `review_reason`, `suggested_reply`, `source_ids`, and `sources`.

Input limits are 100 characters for the ticket ID, 200 for the subject, and
10,000 for the message. Empty fields and unexpected fields are rejected.

Authentication errors return 401; missing server-side API-key configuration returns
503. Invalid input returns 422. Handled upstream/model-validation failures return
502, and xAI timeouts return 504. `/health` does not call or validate xAI.

## Validation and results

The following checks passed during project deployment:

- **24 automated tests:** 14 schema/result-validator tests and 10 API tests.
  These mock retrieval and xAI; they do not measure language-model accuracy.
- **Linux container check:** image build, CPU-only PyTorch check, dependency check,
  unit tests, real cached-model startup, `/health` reporting six documents,
  and rejection of a request without an API key.
- **Manual deployed checks:** blocked account after payment, suspected account
  takeover, and an out-of-scope cake-recipe question, confirmed through Streamlit.

Run the existing tests locally:

```powershell
python -m unittest discover -v
```

The small retrieval check in `evaluate_search.py` previously retrieved the expected
document at Top-1 and Top-3 for all six examples. This is a development sanity check,
not evidence of broad retrieval quality.

| Manual scenario | Expected behavior |
| --- | --- |
| Blocked account after payment | `billing`, `high`, KB-001, human review |
| Suspected account takeover | `security`, `urgent`, KB-006, human review |
| Cake-recipe question | Insufficient knowledge, no sources, human review |

Exact reply wording can vary between model calls.

## Deployment configuration

### Hugging Face Spaces

The Docker image listens on port 7860, runs as a non-root user, and uses one Uvicorn
worker. It downloads the embedding model during the build and loads it offline at
runtime. The image includes the knowledge base; persistent storage is not required
for the current read-only design.

Configure `XAI_API_KEY` and `TRIAGE_API_KEY` as Space **Secrets**, and `XAI_MODEL`
as a **Variable**. `.dockerignore` permits only the required build inputs.

### Streamlit Community Cloud

Deploy `app.py` from `main` with Python 3.13 and `requirements.txt`. Set these values
in the app's Secrets settings, replacing the placeholders:

```toml
TRIAGE_API_URL = "https://skiman1357-support-ticket-triage-api.hf.space"
TRIAGE_API_KEY = "SAME_KEY_AS_THE_BACKEND"
DEMO_ACCESS_CODE = "SEPARATE_VISITOR_CODE"
```

Use the API base URL without `/health` or `/triage`. The xAI API key belongs only
on the backend. GitHub Actions checks the container; it does not automatically
deploy changes to Hugging Face. Backend changes must be uploaded to the Space.

## Limitations

- This is a portfolio MVP built around six synthetic documents, not a production
  customer-support system.
- Model-generated classifications, priorities, and replies may be wrong. Validation
  checks structure and source membership, not the truth of every sentence.
- Human review is a flag in the result, not an integration with a real support queue.
- There is no global request limiter, per-user quota, or application-level spending
  cap. Analyses can incur xAI charges; share the demo code selectively.
- Ticket text and retrieved documents are sent to xAI for analysis. Use synthetic
  data in this demo.
- The application does not implement durable ticket history or a multi-user identity system.
- Direct dependencies are pinned, but transitive dependencies, the Docker base-image
  tag, and the embedding-model revision are not fully locked.

Potential next steps include request limits, a broader labeled evaluation set,
retrieval-threshold evaluation, and improved operational logging.
